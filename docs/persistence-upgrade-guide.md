# 数据库与配置文件长期维护和升级指南

本文面向 JobTrail 维护者，约定正式发布后的数据库、配置、备份和客户端升级方式。数据库现有结构见 [database.md](database.md)，项目开发约束见 [CLAUDE.md](../CLAUDE.md)。

**统一迁移入口已实现。** 当前目标为数据库结构版本 2、配置结构版本 1；正式数据库迁移白名单为 `1 → 2`，配置白名单目前为空。下文通用规则继续约束后续版本，涉及未来版本的数字仅为示例。

实现入口为 `src/main/persistence-migrations.ts`：`planPersistenceUpgrade` 计算连续路径；`preparePersistenceUpgrade` 校验并转换隔离副本；`ensurePersistenceReady` 协调桌面启动、维护独占、快照、替换及中断恢复。数据库和配置采用独立的 `MigrationStep` 白名单，每步显式声明 `from`、`to` 和固定转换函数。客户端版本仅作展示。

迁移状态位于受控 `.runtime/persistence-upgrade/`，包括进程所有者、来源副本、目标副本与 prepared/applying/committed 日志。替换中断恢复整套来源；已提交状态核验后继续。迁移失败时保留来源副本；原始配置与备份的加密机制不变。

根启动器的更新健康检查期间，桌面在 `JOBTRAIL_LAUNCH_TOKEN` 指定的受监督启动下借用现有维护冻结，迁移完成后仍由根启动器解除冻结。普通启动创建并管理自己的冻结，等待 MCP 退出后再迁移或恢复未完成判题；MCP 和 worker 只打开当前目标版本，不争抢迁移。

新增版本时：冻结来源 schema；提高对应目标结构版本；追加唯一连续迁移步骤；补充来源/目标校验和固定样本；保证最新初始化结构与完整迁移链结果一致；更新 database.md；执行启动与旧备份导入往返测试。已发布步骤及 v1 样本不可改写。

## 1. 当前能力与后续边界

| 项目     | 当前行为                                                                         | 持久化格式改变时需要补充                       |
| -------- | -------------------------------------------------------------------------------- | ---------------------------------------------- |
| 数据库   | 新库初始化为 `user_version = 2`；桌面将正式 v1 迁移至 v2，其他不支持版本拒绝打开 | 从已发布正式结构逐级迁移到目标结构             |
| 配置     | AES-256-GCM 加密；解密后严格校验完整 `configVersion = 1` 对象                    | 按来源版本校验、转换，再加密保存               |
| 配置损坏 | 保留原文件，明确报错；不使用默认值覆盖                                           | 继续保持这一原则，区分损坏与可迁移的旧格式     |
| 软件更新 | 创建数据库、配置回滚点；新版启动健康检查失败时支持恢复旧程序和快照               | 将数据库与配置迁移纳入启动、恢复和健康检查顺序 |
| 备份导入 | 按来源版本校验、在临时副本迁移至目标格式；支持恢复中断回滚                       | 对旧正式版备份在临时副本中执行同一套迁移       |
| 公司目录 | 新库从包内目录初始化；已有数据库通过设置按钮更新                                 | 内容变化递增目录版本，不自动混入数据库迁移     |

首个正式版之前的开发数据不在兼容范围内。开发库的一次性手工整理，与正式用户数据迁移是两件事。

1.0.0 已正式发布。从此以后，修改已发布的数据格式就需要提供可验证的升级路径。不能将“没有测试版兼容代码”理解为“后续正式版本也不需要迁移”。

## 2. 独立管理各类版本

| 版本               | 存放位置或含义                                               | 何时变化                                   |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------ |
| 客户端版本         | `package.json` 的 `version`                                  | 发布新的客户端                             |
| 数据库版本         | SQLite `PRAGMA user_version`，代码目标值 `DB_SCHEMA_VERSION` | 表、列、索引、约束或持久化数据语义改变     |
| 配置数据版本       | 解密对象中的 `configVersion`                                 | 字段、嵌套结构、类型、枚举或持久化语义改变 |
| 配置加密封装版本   | 加密 JSON 外层的 `version`                                   | 封装字段、算法或认证协议改变               |
| 加密密钥标识       | 加密封装中的 `keyId`                                         | 加密密钥改变；不等于配置结构版本           |
| 备份格式版本       | 备份封装及清单中的格式标识、版本                             | 归档布局、加密封装或清单协议改变           |
| 公司目录格式版本   | `formatVersion`                                              | 公司目录 JSON 的结构或解释规则改变         |
| 公司目录内容版本   | `catalogVersion`                                             | 行业或公司内容改变                         |
| 目录最低客户端要求 | `minimumAppVersion`                                          | 新目录需要较新客户端才能正确处理           |

客户端升级不必同时提高数据库或配置版本。例如，纯界面调整可以继续使用原数据版本；新增配置字段则应提高配置版本，但未必需要改变数据库版本。

数据库版本也覆盖表内 JSON、聊天事件、工具结果、附件引用、LangGraph checkpoint 和中断负载的语义。升级相关依赖时，即使建表 SQL 没变，也必须验证已保存的数据能否继续读取和使用。

只调整“首次创建配置时”的默认值，不一定需要提高配置版本；不能因此重写现有用户的设置。如果需要改变既有数据的含义或取值，应设计明确迁移。

## 3. 跨客户端版本升级

1.0.0、1.1.0、1.2.0 均使用数据库和配置结构版本 1；1.3.0 的实际目标为数据库 2、配置 1。表中 1.4.0 仅为后续同时升级两种结构的示例：

| 客户端        | 数据库版本 | 配置版本 |
| ------------- | ---------- | -------- |
| 1.0.0         | 1          | 1        |
| 1.1.0         | 1          | 1        |
| 1.2.0         | 1          | 1        |
| 1.3.0         | 2          | 1        |
| 1.4.0（示例） | 3          | 2        |

上述示例中的 1.4.0 必须保留数据库的 `1 → 2`、`2 → 3`，以及配置的 `1 → 2` 转换。本次 1.3.0 不需要配置空迁移，原设置、模型配置及 API Key 保留。

| 用户来源                         | 数据库执行路径 | 配置执行路径   |
| -------------------------------- | -------------- | -------------- |
| 1.0.0、1.1.0 或 1.2.0 升到 1.4.0 | `1 → 2 → 3`    | `1 → 2`        |
| 1.3.0 升到 1.4.0                 | `2 → 3`        | `1 → 2`        |
| 已运行过 1.4.0                   | 不迁移         | 不迁移         |
| 全新安装 1.4.0                   | 直接创建结构 3 | 直接创建配置 2 |

用户不需要先安装 1.3.0。最新客户端根据数据库和配置各自的版本选择迁移链，不根据客户端版本猜测数据格式。

两个数据版本不要求相等。例如，未来某个客户端可能只升级数据库，其配置仍为旧版本。发布时应记录实际支持的版本组合；在断电恢复或人工替换文件后遇到不一致组合，先检查恢复日志，不能直接把它当成正常来源继续运行。

维护规则：

- 已发布的迁移步骤保持稳定，后续版本追加新步骤；已发布样本不得重写。
- 迁移路径必须连续。缺少 `2 → 3` 时，不能直接将版本号改成 3。
- 保留从所有承诺支持的正式版升级所需的步骤。将来缩短支持范围，需要单独制定用户恢复方案。
- 修复已发布迁移中的缺陷时，应同时考虑已经迁移成功和尚未迁移的用户。不能只改历史步骤后假设所有用户都会重新执行。
- 不提前创建空迁移、通用字段猜测器或测试版转换入口。已有统一迁移基础设施，下一次结构变化只追加真实步骤及其校验。

## 4. 数据库迁移规则

### 4.1 读取、规划与校验

启动时先处理未完成的恢复记录，再读取数据库版本。此时不启动业务写入、MCP、智能体或提醒调度。

| 数据库情况                     | 行为                                     |
| ------------------------------ | ---------------------------------------- |
| 确认是全新数据库               | 创建目标结构并初始化种子数据             |
| 低于目标版本，且有完整迁移链   | 校验来源结构，准备备份和迁移             |
| 等于目标版本                   | 不重复执行迁移                           |
| 高于目标版本                   | 拒绝写入，提示使用支持该数据的较新客户端 |
| 版本不合法、结构损坏或缺少路径 | 保留原数据，明确报错                     |

不能把“`user_version = 0` 但已经包含未知业务表”的数据库当成空库补建或自动修复。当前初始化和迁移入口均校验来源结构，拒绝这类异常来源。

来源校验应依据该正式版本的结构及关键约束。版本号是路径选择依据，但单独修改一个版本号不能让不符合该结构的数据库通过校验。

### 4.2 编写迁移步骤

每一步明确来源版本、目标版本、字段变化、数据处理规则和校验条件。SQL 使用固定、可审查的表列名；业务数据使用参数绑定。

常见情况：

- 新增字段：确定可空性、默认值及旧记录的业务含义。必须补齐的值由该迁移显式写入。
- 新增唯一约束：先明确如何处理旧数据中的重复值，不能遇到重复就任意删除记录。
- 重命名、拆分或重建表：显式列出复制字段，保留主键、关联和必要时间信息，验证行数及引用。
- 修改枚举或 JSON：依据来源格式转换并校验目标语义，不在日常读取时同时保留两套解析。
- 改变索引或约束：同步更新新库初始化定义，并验证迁移后的结构一致。

迁移可以使用明确的 `ALTER TABLE` 或表重建 SQL。这是正式版升级逻辑，不是对任意旧开发库的自动兼容。

不要使用当前版本的公司目录同步、仓储映射或默认配置来解释历史结构。它们未来可能变化；迁移需要使用属于该步骤的固定 SQL、来源定义和常量，避免同一迁移在不同客户端中产生不同结果。

### 4.3 事务和中断

常规迁移在一个 `IMMEDIATE` 事务内执行本次所需的全部步骤。比如 `1 → 2 → 3`，第二步失败时第一步也回滚，数据库仍为版本 1。

目标结构和业务不变量校验成功后，在同一事务中写入目标 `user_version`，再提交。未成功提交时不得提前标记完成。

不要把网络请求、附件改写、配置文件替换或 SQLite 不允许在该事务内执行的维护命令放进迁移事务。需要大规模、分阶段迁移时，应另行设计进度和恢复协议，不能悄悄拆成几个独立提交。

重启后的恢复由版本和持久化恢复记录决定。通过事务保证未提交的步骤重做，通过目标版本保证已提交的步骤不重复执行，而不是用“字段存在就跳过”掩盖不确定状态。

## 5. 配置迁移规则

每个 `persistence/config-vN.ts` 保存该配置版本的完整校验规则和用于新建配置的默认值。当前 `ConfigService` 与迁移入口共同复用 `config-v1.ts` 的规则，配置默认值先通过校验再加密落盘。新增配置版本时，保留已发布版本的校验规则，并显式切换当前配置服务使用的版本定义；迁移步骤需要补充字段时使用该步骤固定的值，不依赖随客户端变化的新建默认值。

配置需要先认证解密，再依据来源 `configVersion` 校验。不能先套用最新严格 schema，把合法旧格式误判成损坏。

推荐顺序：

```text
读取加密封装
→ 校验受支持的封装格式和密钥标识
→ AES-GCM 认证解密
→ 读取 configVersion
→ 按来源版本严格校验
→ 逐级转换
→ 按目标版本严格校验
→ 使用当前约定的封装重新加密
→ 暂存，等待与数据库一起提交
```

配置转换应为无文件副作用的函数：接收已校验的旧对象，返回完整新对象，不在中间步骤落盘。

例如，版本 2 新增一个通知开关：`1 → 2` 中明确为旧用户设置什么值，并保留主题、API Key、MCP 开关等其他设置。这个值属于迁移规则，不能直接引用未来可能变化的 `DEFAULT_CONFIG`。

必须区分：

- 合法旧配置没有未来新增的字段：通过对应版本迁移补充。
- 配置缺少其自身版本已经要求的字段：属于损坏，不使用默认值自动修复。
- 全新用户没有配置文件：创建目标版本的完整默认配置。
- 恢复记录表明文件替换尚未完成：先恢复，不能把暂时缺失误判为新用户。

解密失败、未知版本、无效字段或缺少迁移链时，保留原文件并提示，不重置配置，不删除 API Key。

## 6. 数据库与配置的联合提交

**SQLite 事务与配置文件的原子 rename，不能组成跨文件事务。** 如果数据库已经升到版本 3，而配置仍为版本 1，直接开放业务可能造成数据损坏。因此第一次同时涉及两者的升级，必须增加启动级的恢复协调。

已采用“暂存副本＋恢复日志”的方式；启动迁移与备份恢复使用各自的提交日志，共享转换及版本校验。

1. 获得安装数据目录的维护独占权，阻止其他桌面实例、MCP 和后台任务写入；已有操作先结束。
2. 检查并完成未结束的恢复流程，确定一致的来源数据库和配置。
3. 为来源数据创建经校验的回滚副本；数据库使用 SQLite 在线备份，包含已提交 WAL 内容，不能只复制正在使用的 `.db` 文件。
4. 在暂存目录中迁移数据库和配置，校验最终结构、业务引用、配置及目标版本组合。
5. 写入持久化恢复日志，再在关闭数据库连接的情况下替换正式数据。日志记录来源与目标版本、受控路径、校验值和提交阶段，不记录配置明文或密钥。
6. 数据组合提交并核验成功后，启动业务服务。发生异常或断电时，下次启动先根据日志完成提交或恢复来源组合。
7. 新版完整启动并通过健康检查后，才结束升级保护；在这之前保留可用回滚点。

恢复协议必须能处理“替换数据库后断电”“替换配置后断电”“完成替换但尚未标记提交”等状态。不能只依靠一个内存布尔值，或看到目标数据库版本就认定整个过程成功。

替换数据库时还要协调 WAL/SHM 文件，避免旧侧文件污染恢复后的数据库。不要在仍有连接使用时删改这些文件。文件替换和恢复日志应采用受控路径，并考虑同卷 rename、写入持久性和文件占用。

内部迁移需要专门的维护入口，不能通过放开正常业务写保护来执行。现有更新冻结状态还未解除时，迁移协调器也不能直接调用会被业务冻结拦截的普通 Service。

## 7. 与客户端更新、根启动器和 MCP 的协作

Velopack 负责程序文件更新，不会自动替 JobTrail 迁移数据库和配置。迁移由新版客户端在开放业务前完成。

当前根启动器已有升级健康检查、旧程序及数据快照恢复机制。已接入启动迁移，维持以下顺序：

```text
旧客户端冻结写入并创建回滚点
→ Velopack 安装新版
→ 根启动器启动新版
→ 恢复未完成操作并完成数据迁移
→ 初始化业务并挂载界面
→ 报告健康
→ 完成更新提交
```

不能为了避免启动超时，在迁移完成前报告健康。当前根启动器有 45 秒健康等待窗口；迁移设计需要评估大库耗时。如果不能在现有契约下完成，应先设计旧启动器可理解的升级方案，不能假设新启动器已先替换。

软件回滚必须恢复匹配的旧数据库和旧配置，不能只降级程序。迁移失败可恢复升级前快照；但新版已经长期使用后，再恢复旧快照会丢失期间新增数据，不能把它当成任意时刻的无损降级方案。

MCP 可能在桌面客户端之前启动。它必须检查维护状态和数据版本，不能绕过迁移直接打开旧结构，也不能与桌面同时迁移。只有桌面启动入口负责迁移；MCP 遇到需要迁移的数据时返回明确错误，要求先启动桌面客户端，不弹窗、不污染协议输出。

手动安装新版、直接启动新版和跳过多个版本升级，也必须经过同一数据检查入口，不能只在“点击软件更新”这条路径中迁移。

## 8. 旧备份导入

备份是否可恢复主要取决于备份、数据库、配置和加密格式，不仅是创建备份的客户端版本。

后续支持旧备份的流程：

1. 验证归档封装、密钥、路径、大小、哈希和清单。
2. 按清单声明的来源版本校验数据库结构、配置和文件引用，而不是直接用最新 schema 拒绝旧格式。
3. 在临时恢复副本中执行与启动升级相同的数据库和配置迁移。
4. 按目标版本再次验证数据库结构、业务数据、简历和聊天附件引用。
5. 使用目标配置加密封装生成恢复文件，交给恢复协调器提交。
6. 失败时丢弃未提交的临时工作，保留当前使用中的数据和用户原始备份。

数据库或配置来自未来不支持的版本、缺少迁移路径、内容损坏或密钥不匹配时，拒绝恢复。不能强行降低版本号、忽略字段或覆盖当前数据。

启动迁移与备份导入共用数据转换步骤，但使用各自的提交上下文：前者升级当前安装数据，后者准备一个待覆盖恢复集。不要在导入校验阶段就修改当前数据库。

## 9. 加密密钥与封装维护

同一发行渠道的构建密钥必须长期保持一致，并由维护者安全保存。`private-build.config.json` 继续保持 Git 忽略，不进入开源仓库、日志或测试报告。

数据库版本变化、增加配置字段或升级客户端，都不要求更换密钥。每次重新加密应使用新随机 IV，不能复用固定 IV。

密钥轮换与普通配置迁移不同。当前实现只支持当前构建密钥，不能仅换一个私有构建文件的值就发布。轮换前至少明确：

- 新客户端如何读取已安装的旧加密配置。
- 用户多年以前导出的备份如何恢复。
- 旧密钥的受控保留、选择和停用策略。
- 升级中断或软件回滚后使用哪套密钥和封装。

不得为了容错加入明文读取、默认密钥或解密失败后重置配置。`keyId` 只是密钥标识，不是可以恢复密钥的内容。

当前备份沿用构建密钥，不要求用户单独设置密码。维护者丢失密钥会直接影响历史配置和备份的可恢复性；密钥备份应独立于普通代码仓库管理。

## 10. 公司目录与数据库迁移的边界

现有用户升级客户端时，不自动合并包内新增的行业和公司；仍由设置中的“更新内置公司”统一同步。首次创建新数据库才导入包内目录。

新增公司、调整行业、将退出目录的公司转为自定义，通常是目录内容变化，应递增 `catalogVersion`，不是重新 seed 数据库，也不必提高 `user_version`。

若新目录依赖旧客户端不具备的行为，例如退出目录时必须执行新的转换规则，需要合理设置 `minimumAppVersion`。仅上传 JSON 不能让旧程序获得新业务逻辑。

迁移步骤不得访问在线目录或直接使用以后变化的包内目录进行历史数据转换；确有需要时，迁移应携带固定的转换规则，正常目录更新继续保持独立。

## 11. 测试与发布验收

### 11.1 冻结正式版样本

保留 `tests/fixtures/v1/` 的合成数据库、配置和附件基线及哈希。未来新增正式格式样本时添加新目录，不重写旧样本来让测试通过。固定样本和单元测试使用公开专用密钥；安装包验收将合成配置重新加密为本次构建密钥，以验证真实安装包。密钥不输出、不提交，所有业务数据均为合成数据。

样本至少覆盖：公司与自定义行业、收藏和已读状态、求职记录及状态历史、日程、简历文件、多轮聊天、工具结果、模型用量、附件以及等待用户输入的任务状态。

### 11.2 必须覆盖的路径

| 场景                           | 验证内容                           |
| ------------------------------ | ---------------------------------- |
| 最早支持版本直接升最新版       | 完整迁移链、用户数据和配置保留     |
| 每个中间正式结构升最新版       | 每一条来源路径均可执行             |
| 最新版重复启动                 | 不重复迁移、不覆盖设置             |
| 全新安装                       | 最终结构与迁移到最新版的结构一致   |
| 数据库与配置分别变化           | 独立版本选择和合法组合校验         |
| 各迁移步骤注入失败             | 数据库事务回滚，版本号不提前提交   |
| 联合替换各阶段被中断           | 重启后恢复一致的数据组合           |
| 新版业务初始化失败             | 旧程序与旧数据库、旧配置一起恢复   |
| 每个支持版本的备份导入         | 临时迁移成功；失败不污染当前数据   |
| 新客户端创建的数据交给旧客户端 | 拒绝不支持的未来格式，不破坏数据   |
| MCP、智能体或提醒正在工作      | 先完成维护隔离，再迁移；无并发写入 |
| 配置损坏、密钥错误、路径缺失   | 明确报错，原始数据保留             |
| 大库、WAL、空间不足、文件占用  | 耗时满足启动契约，失败可恢复       |

验收不能只检查 `user_version` 或“应用能打开”。还要比较主键与引用、记录数量、重要字段、配置取值、文件内容哈希，以及迁移后新建、修改、删除和备份恢复是否正常。

### 11.3 1.3.0 可重复安装包验收

执行 `pnpm package:win` 后：

- `pnpm test:compatibility:package` 从历史提交 `3acb686`（1.0.0）、`d277149`（1.1.0）、`a430f37`（1.2.0）提取原始导出代码，分别生成数据库/配置均为 v1 的真实加密备份。逐一在 1.3.0 安装包通过正式 IPC 导入、退出、启动、读取，再导出新版备份并导入、重启、读取。另对 1.1.0、1.2.0 原始数据目录验证首次自动升级及第二次启动。
- 验收比对业务记录、聊天事件、模型用量、checkpoint/writes、配置内容、简历及附件哈希，并读取仍在等待用户回答的聊天。目标为数据库 v2、配置 v1；备份导入替换已有合成记录，不能混入新旧数据。
- `pnpm test:exams:package` 在安装包内通过 `/study` 和实际 MCP 逐题生成，验证出题进行时独立 worker 完成简答评分、客观题提交、重启保存、试卷备份导出/删除原聊天/导入/重启及整卷重置。模型服务使用本地确定性响应，不调用付费外部模型。
- 兼容性样本和报告保存在忽略目录 `dist/compatibility/`，来源提交写入 `report.json`。脚本仅操作隔离目录；重启时保留正式导入退出与启动恢复流程，由 Playwright 接管新进程以便断言。

### 11.4 每次正式发布前

1. 列出本次客户端、数据库、配置、封装、备份和目录版本，说明哪些变化、为什么变化。
2. 确认每个受支持来源版本都存在迁移路径，并有历史样本测试。
3. 更新新库定义、目标配置 schema、来源迁移、备份校验、版本错误提示和相关文档。
4. 在隔离安装中进行低版本直升、重启、旧备份恢复及升级失败回滚验收。
5. 验证构建密钥、发布标签、包版本、目录清单与资产哈希正确。
6. 通过对应类型、格式、单元和集成测试及发布构建；源码版本与测试安装包一致。
7. 发布说明明确数据格式变化、支持的升级来源和恢复限制。

已经公开的正式版本及其资产应保持可追溯。修复正式用户可能已经使用的持久化问题时发布新客户端版本，不能覆盖旧包后仍假定所有同版本用户拥有相同数据行为。

## 12. 代码职责

| 当前文件                             | 职责                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| `src/main/persistence-migrations.ts` | 版本规划、白名单、隔离迁移、桌面联合提交与恢复               |
| `src/main/persistence/`              | 目标版本常量、冻结历史 schema、v2 SQL 及结构/试卷数据校验    |
| `src/main/database.ts`               | 创建目标新库、拒绝不支持的版本、校验目标结构                 |
| `src/main/config.ts`                 | 目标配置、严格校验、常规配置读取与保存                       |
| `src/main/config-crypto.ts`          | 加密封装、认证解密和密钥边界，与配置字段迁移分开             |
| `src/main/desktop.ts`                | 在业务启动之前接入统一维护与迁移协调                         |
| `src/main/backup-archive.ts`         | 按来源版本验证备份，在临时副本迁移后验证目标格式             |
| `src/main/backup-restore.ts`         | 恢复集提交与中断恢复，与启动迁移协调器共享必要的文件恢复机制 |
| `src/main/update-rollback.ts`        | 保存匹配的来源数据库与配置，为升级失败提供回滚点             |
| `native/bootstrap/`                  | 保持旧启动器可执行的启动、健康检查和软件回滚契约             |

新增迁移步骤和协调模块时，应把它们集中在持久化边界。业务 Service、Renderer 和 MCP 工具只接收目标结构，不各自处理旧字段。

每次结构升级必须一起维护具体版本迁移、来源与目标校验、联合提交恢复、MCP 维护限制、旧备份迁移、升级回滚验证和文档。
